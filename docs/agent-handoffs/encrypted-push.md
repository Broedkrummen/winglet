# Encrypted push — implementation contract

Capability: encrypted_push, envelope v1. Android uses the maintained UnifiedPush connector with the user's ntfy distributor and the server's configured HTTPS ntfy origin. An application AES-256-GCM envelope is additionally bound to server/device/key/version/purpose, then sent using existing RFC8291 Web Push encryption. The relay receives no bot/chat/title/action plaintext. Existing browser Web Push remains RFC8291 encrypted; its receive/action validation is upgraded separately.

Native keys are random per pairing/key generation, wrapped with a non-exportable Android Keystore AES key, stored only in no-backup app storage. Provisioning goes through the pinned server's existing X25519 sealed-secret channel and current verified-device signature. The trusted gateway necessarily holds the delivery key. Rotation replaces the server subscription atomically and retires previous keys locally; reinstall/key loss requires explicit repair. Opt-in is sticky: an old client cannot silently restore plaintext ntfy delivery. Unpairing removes delivery subscriptions; local pairing removal tears down local keys/notifications. A replay cache is persisted before display, bounded to the age window, and refuses new work when full instead of evicting live IDs.

UI: Notifications → encrypted Android delivery, explicit distributor choice/setup, optional unlocked previews default off, rotate/repair, turn off and diagnostics. Subscription/relay acceptance/receipt/decryption/display are different stages. Missing distributor, permission denied, offline/version mismatch/key loss are actionable and preserve existing app use. Approvals always open Winglet for current authenticated review. No push handler sends a reply or approves anything.

## Implementation and review

- Native receiver/module: `app/modules/winglet-push`, Android26+, connector3.3.5. No Google Firebase account, Winglet relay, wake lock or app-owned permanent network service is added. The installed ntfy distributor owns background connectivity. The current server's configured HTTPS ntfy origin is the only permitted delivery origin; signed members cannot choose an arbitrary internal HTTP target.
- Routes: GET `/api/push/encrypted` is current-device read-only; POST/DELETE require the current verified device signature. POST accepts only a `push-key` sealed secret for that exact pairing. The handler rechecks pairing/signing identity after body I/O. Device IDs in input cannot select another recipient.
- Registration compares the previous key ID and monotonically increasing endpoint revision inside a SQLite transaction. A delayed endpoint repair cannot roll back a newer key/endpoint or re-enable a revoked subscription. A native activation also compares both key and endpoint revision. The UI waits for a fresh distributor callback, not an old cached endpoint.
- Storage reuses `push_subs` with kind `encrypted-v1` plus `kv` keys `push.encrypted.<device-id>`. Enrollment atomically retires old ntfy/web delivery routes while retaining address recovery. Device unpairing removes the subscription and key material. The privacy marker remains to block an old client silently restoring plaintext; it contains no key or message. No numeric global migration is allocated.
- Android key records, receiver diagnostics and replay IDs are encrypted with per-pairing non-exportable Android Keystore wrapping keys in no-backup storage, using AtomicFile. Delivery keys enter JS memory only for pinned sealed enrollment, never Zustand persistence or the offline outbox. Explicit rotation also repairs an invalidated wrapping key. Reinstall/key loss requires repair; no plaintext route is substituted.
- Envelopes use random96-bit GCM nonces and unambiguous length-prefixed UTF8 AAD binding protocol/version/server/device/key/purpose. A bounded inner payload carries random delivery identity, issuance and at-most24h expiry. Only known note fields are included; approvals/actions/extra fields are omitted. The native receiver requires successful RFC8291 transport decryption as well as application authentication.
- Replay records are committed before display and survive worker restart. Live records are never evicted to admit a replay. Overflow fails closed. Native capture/display requires no network round trip or gateway credentials. Server mutes/quiet hours and per-device foreground suppression remain authoritative; test/approval nudges are not incorrectly suppressed just because Winglet is open.
- Previews default off. Actual device lock is checked; detailed notifications use SECRET lock-screen visibility. App lock uses generic previews and removes previously detailed notifications when its policy changes. Android may retain opted-in details in OS notification history; Winglet does not persist message bodies in its push storage. OS notification permission/channel/Focus settings remain authoritative.
- Root lifecycle bridge removes keys/subscriptions after local pairing removal or observed unauthorized pairing state. Endpoint migrations of previously activated registrations repair while Winglet is open and online; a first registration still requires user setup. Background distributor endpoint changes wait for this authenticated foreground repair instead of storing gateway credentials in the receiver.
- Browser Web Push continues existing RFC8291 transport encryption. Re-registration negotiates guarded payloadv1, persists expected server/device scope and an expiry/replay cache in IndexedDB before versioned delivery begins. Existing legacy subscriptions remain usable until opt-in; thereafter malformed/legacy payloads fail closed. Local pairing removal closes even the legacy receive path. All notification clicks, including cached old approval buttons, open the current authenticated UI; no service-worker approval POST remains.
- Shared files: hub dispatch/routes/status, notification/setup UI, root bridge, client push registration/types and connection diagnostics. Generated dependency notices include full Apache2 text for UnifiedPush and its Tink dependency; no upstream source was modified or vendored.

## Evidence and remaining device checks

- Native Kotlin compile, five native JUnit tests (independent Python→JCA AES-GCM vector/tamper/scope checks and replay/expiry/restart/capacity cases) and real API36 release-manifest merge passed. No production signing/identity change.
- Full local plugin suite passed632 tests /31 skips; two additional encrypted mute/foreground/version-negotiation tests then passed in the20-test feature suite. Full client suite passed440 tests, and the additional legacy-unpair worker test passed in the12-test feature suite. TypeScript and production web export passed; CI supplies the final combined counts and Android bundle check.
- A real Chromium service worker displayed a synthetic local test notification, restarted, then refused replay/wrong-device/expired payloads. This exercised real browser notification APIs and persistent worker state via CDP synthetic push transport; it did not prove an external relay delivered a push. Local fixture notifications were closed afterwards.
- The actual Android-settings React component was rendered in an isolated browser using an injected synthetic native port. Settings/diagnostics checked at320/390/768/1440, light/dark and reduced motion; no horizontal overflow, long names wrap, preview choice survived refresh, and diagnostics scroll. Screenshot review caught and fixed a missing visible switch label. This is layout evidence, not Android-native runtime evidence. The private fixture route was removed from source after export.
- MOBILE VALIDATION PENDING: real ntfy distributor enrollment/callback, native bridge values and Android13+ permission flow, platform Keystore/AtomicFile behavior, background/terminated/reboot delivery, airplane-mode backlog/expiry, rotation/key invalidation/reinstall repair, pairing revoke, lock-screen/app-lock previews and notification navigation. OEM battery/Doze/vendor restrictions need physical-device coverage. No user's phone subscriptions, keys or permissions were changed for these tests. Quiet/mute policy is evaluated at send time; an already queued push can arrive after settings change.
- Rollback: old code ignores `encrypted-v1`; opted-in devices then receive no legacy plaintext fallback. Update/reinstall the current Android build and repair enrollment. The existing published v0.6.0 artifacts do not contain this feature; this PR does not publish a new release.

## Reference comparison and privacy boundary

| Reference behavior | Winglet result | Difference / evidence |
|---|---|---|
| Signed/encrypted ntfy payloads and freshness guard | Device-scoped AES-GCM plus RFC8291, persistent replay/expiry policy | Native vector/guard and backend tests; actual Android delivery pending |
| App-owned long-lived ntfy stream | Maintained UnifiedPush distributor transport | Avoids another Winglet background service; distributor setup required |
| Pinned sender registration | Existing verified-device signature and pinned sealed-secret provisioning | Symmetric endpoint authentication; trusted gateway holds delivery key |
| Push nudge/actions | Current authenticated Winglet review | No notification approval/reply execution |
